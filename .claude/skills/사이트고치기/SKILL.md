# 사이트를 고칠 때

주인이 사이트를 자기 것으로 바꾸는 건 좋은 일입니다. **작게 고치든 통째로 새로 짜든 막지 않습니다.**

내가 할 일은 말리는 게 아니라 **되돌아올 자리를 만들어 두고, 쌓인 글이 안 없어지게 챙기는 것**입니다.

> 사이트의 화면·기능·구조를 손대는 요청이면 **시키지 않아도 이 규칙을 따릅니다.**
> 글을 쓰거나 고치는 건(`src/content/`) 해당 없습니다 — 그건 마음껏 해도 안 무너집니다.
> 크게 갈아엎고 싶다면 **[크게 바꾸고 싶을 땐](#크게-바꾸고-싶을-땐-전면-개편)**으로 바로 갑니다.

---

## ★ 이 사이트의 뼈대 — 넷만 기억하면 됩니다

| 자리 | 무엇 | 주인이 손대나 |
|---|---|---|
| `src/content/` | **글** — 학습일지·사례글·개념·프로젝트 카드 | **매일 손댐** (마음껏) |
| `src/content/config.ts` | 글에 어떤 항목이 들어가는지 정하는 곳 | 가끔 (항목 추가할 때) |
| `src/lib/` | **글을 불러오고 정렬하는 곳** | 거의 안 함 |
| `src/pages/` · `src/components/` | 화면 | 꾸밀 때 |

**글과 화면이 분리돼 있는 게 이 사이트의 핵심입니다.** 화면을 아무리 고쳐도 글은 안전하고, 글을 아무리 써도 화면은 안 깨집니다.

---

## 고치기 전 — 세 가지를 먼저 합니다

### 1. 지금 뭐가 되는지 확인합니다

```
npm run dev
```

지금 잘 되는 화면을 눈으로 보고 시작합니다. **무엇이 깨졌는지 알려면 안 깨진 상태를 먼저 봐야** 합니다.

### 2. 되돌릴 수 있게 해둡니다

```
지금까지 잘 되는 상태를 커밋해줘. 고치다 잘못되면 여기로 돌아올 거야.
```

### 3. 지금 구조를 읽습니다

바로 만들지 않습니다. **비슷한 게 이미 있는지** 먼저 봅니다. 있으면 그 방식을 따라갑니다 — 새 방식을 하나 더 만들면 그때부터 두 가지를 다 관리해야 합니다.

---

## 지킬 규칙 다섯

### ① 같은 것을 두 군데 적지 않습니다

화면에 뜨는 이름표·색·반복되는 문구는 **한 곳에서만** 정합니다.

- 종류·상태 이름표 → `src/lib/labels.ts`
- 사이트 이름·인사말 → `src/config/site.ts`
- 색·간격 → `src/layouts/Base.astro` 맨 위의 `:root` 변수

> 이 사이트도 예전엔 이름표가 네 파일에 복사돼 있었습니다. 종류를 하나 추가할 때 네 곳을 고쳐야 했고, 한 곳만 빠뜨리면 **그 화면에서만 빈칸**이 떴습니다. 그래서 한 곳으로 모았습니다.

### ② 글을 읽어오는 건 `src/lib/`에서만

화면 파일에서 `getCollection`을 직접 부르지 않습니다. `src/lib/content.ts`의 함수를 씁니다.

필요한 게 없으면 **거기에 함수를 하나 더 만들고** 화면에서 가져다 씁니다. 그래야 나중에 글의 항목이 바뀌어도 **고칠 자리가 하나**입니다.

### ③ 색은 직접 쓰지 않습니다

`#333` 같은 색을 화면 파일에 박지 말고 `var(--fg)` 같은 변수를 씁니다.

```
--bg  --surface  --fg  --muted  --line  --accent
--green-bg/fg  --amber-bg/fg  --radius
```

나중에 사이트 색을 통째로 바꿀 때 **변수 한 곳만** 고치면 됩니다.

### ④ 반복되면 부품으로 뺍니다

같은 모양이 세 번 나오면 `src/components/`에 부품으로 만들고 셋 다 그걸 씁니다. 두 번까지는 그냥 둬도 됩니다 — 미리 부품으로 만들면 오히려 복잡해집니다.

### ⑤ 한 번에 하나씩, 확인하면서

여러 개를 한꺼번에 고치면 **어디서 깨졌는지 못 찾습니다.** 하나 고치고 → 화면 보고 → 되면 커밋 → 다음.

---

## 고친 뒤 — 반드시 확인합니다

```
npm run build
```

**이게 통과해야 배포됩니다.** 여기서 빨간 글씨가 나오면 지금 고칩니다. 그대로 올리면 사이트가 안 뜹니다.

그리고 눈으로도 봅니다.

- 홈 · 프로젝트 · 학습위키 · 내 서재 **네 화면이 다 열리나**
- 글 하나를 열어서 **본문이 제대로 나오나**
- 휴대폰 크기로 줄여도 **글자가 넘치지 않나**

> ⚠️ **고친 곳만 보지 않습니다.** 한쪽을 고치면 다른 쪽이 깨질 수 있어서, 네 화면을 다 열어봐야 합니다.

---

## 크게 바꾸고 싶을 땐 (전면 개편)

**이 템플릿은 최소 뼈대입니다.** 쓰다 보면 좁아지는 게 정상이고, 그때 크게 바꾸는 건 **막아야 할 일이 아니라 잘 하는 것이 목표인 일**입니다. 주인이 "사이트를 새로 만들고 싶어"라고 하면 말리지 말고 **안전하게 하는 법**을 챙깁니다.

### 크게 바꿔도 되는 이유 — 글과 화면이 분리돼 있습니다

이 사이트의 제일 중요한 성질입니다.

> **화면(`src/pages`·`components`·`layouts`)은 통째로 갈아엎어도 글은 그대로 남습니다.**
> 글은 `src/content/` 안의 마크다운 파일이라, 화면이 어떻게 바뀌든 상관없습니다.

디자인이 마음에 안 들어서 처음부터 새로 짜고 싶다 — **해도 됩니다.** 4주 치 기록은 안 없어집니다.

### 전면 개편할 때 지킬 것 넷

1. **되돌아올 자리를 먼저 만듭니다.** 지금 잘 되는 상태를 커밋하고 시작합니다. 겁 없이 뒤엎으려면 이게 있어야 합니다.
2. **`src/content/`는 건드리지 않습니다.** 화면을 새로 짜는 것이지 글을 다시 쓰는 게 아닙니다.
3. **글을 읽어오는 함수(`src/lib/content.ts`)는 살려둡니다.** 여기가 글과 화면을 잇는 다리입니다. 화면을 새로 짜도 이 함수들을 그대로 부르면 글이 그대로 붙습니다. (다리까지 새로 놓고 싶으면 그것도 되지만, **화면부터 바꾸고 잘 돌아간 뒤에** 손대는 게 안전합니다)
4. **끝나면 글이 다 보이는지 셉니다.** 개편 전 글 개수와 개편 후가 같은지. 화면만 예뻐지고 글이 몇 개 사라진 걸 못 보고 넘어가는 일이 제일 흔합니다.

### 폴더 이름이나 항목을 바꾸려면 — 같이 고칠 곳이 있습니다

못 한다는 게 아니라, **혼자 못 바뀝니다.** 아래를 한 번에 같이 고치고 `npm run build`로 확인합니다.

| 바꾸려는 것 | 같이 고칠 곳 |
|---|---|
| 글 폴더 이름 (`wiki` → 다른 이름) | `src/content/config.ts` · `src/lib/content.ts` · 화면 파일들 · `.claude/skills/` 안의 스킬들 · `.gitignore` |
| 글의 항목 **추가** | `src/content/config.ts` (+ 화면에 보이게 하려면 그 화면) |
| 글의 항목 **삭제** | ★ **먼저 글에서 그 줄을 지우고**, 그다음 config에서 뺍니다. 순서가 반대면 이미 쓴 글이 전부 오류가 납니다. (당장 지우기 싫으면 `.optional()`로 바꿔 두면 있어도 없어도 됩니다) |

### 이것만은 순서를 지킵니다

- **한 번에 하나씩.** 전면 개편이라도 "화면 다 지우고 처음부터"가 아니라, 한 화면씩 바꾸고 확인합니다. 다 갈아엎고 나서 안 되면 어디서 틀렸는지 못 찾습니다
- **막혀서 뒤엎는 것과, 좁아서 뒤엎는 것은 다릅니다.** 막혔을 뿐이면 지금 구조를 먼저 읽고 작은 변경으로 뚫습니다. 그게 아니라 정말 구조가 좁아진 거면 개편이 맞습니다

---

## 새 항목을 만들 땐 (예: 위키에 새 종류 추가)

세 곳을 같이 고칩니다. **하나라도 빠지면 그 자리만 조용히 어긋납니다.**

1. `src/content/config.ts` — 종류 목록에 추가
2. `src/lib/labels.ts` — 화면에 뜰 이름표
3. `src/lib/content.ts`의 `종류순서` — 목록에서 어디에 놓일지

그다음 `npm run build`로 확인합니다.

---

## 왜 이렇게 (학습메이트가 알아둘 것)

- **주인은 코드를 못 읽습니다.** 그래서 "고쳐줘"라고 하면 내가 구조를 지키는 수밖에 없습니다. 규칙을 주인에게 설명하려 하지 말고 **내가 지키면서 뭘 했는지만 한 줄로** 알려줍니다.
- **되돌릴 수 있게 하는 게 제일 중요합니다.** 고치기 전 커밋은 건너뛰지 않습니다. 초보에게 "되돌릴 수 있다"는 안전감이 있어야 이것저것 해봅니다.
- **build 통과는 타협하지 않습니다.** 화면에서 잘 보여도 build가 실패하면 배포가 안 됩니다. 주인은 배포 단계에서야 알게 되고, 그때는 원인이 뭐였는지 못 찾습니다.
- **개편을 말리지 않습니다.** 이 템플릿은 최소 뼈대라 언젠가 좁아지는 게 정상이고, 크게 바꾸는 건 주인이 자기 것으로 만드는 과정입니다. 내가 할 일은 막는 게 아니라 **되돌릴 자리를 만들어 두고, 글이 안 없어지게 챙기는 것**입니다.
