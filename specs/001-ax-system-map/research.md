# Research: 실습용 AX 구조 지도

## 1. 구현 정본과 수업 복사본

**Decision**: 기능의 정본은 `course-renewal/template` Git 프로젝트에 둔다. 지난 수업에서 개인화된 `my-learning-hub` 복사본은 실제 파일 상태를 확인하는 검증 대상으로만 사용한다.

**Rationale**: 원본에 기능을 넣어야 다음 AX 강의에서도 다시 쓸 수 있다. 개인화 복사본을 정본으로 삼으면 대표님의 실습 결과와 공통 템플릿이 섞이고, 이후 수강생에게 배포할 때 매번 수작업으로 걷어내야 한다.

**Alternatives considered**:

- 개인화 복사본에만 구현: 이번 수업은 빠르지만 재사용과 배포가 깨져 제외했다.
- 아루나 사이트에 구현: 공개 사이트가 수강생 PC의 로컬 파일을 읽을 수 없고 콘텐츠·뷰어 분리 원칙에도 맞지 않아 제외했다.

## 2. 실시간 상태 전달 방식

**Decision**: 기존 Astro 개발 서버에 개발 전용 상태 경로를 얇게 연결하고, 지도 화면이 2초 간격으로 상태를 다시 요청한다.

**Rationale**: 현재 프로젝트는 Astro의 기본 정적 출력이다. Astro 공식 문서에 따르면 정적 엔드포인트는 빌드 시점에 생성되고, 요청 때 실행되는 서버 엔드포인트에는 서버 어댑터가 필요하다. 배포 구성을 서버 방식으로 바꾸면 이번 로컬 수업 도구보다 변경 범위가 커진다. 개발 서버에만 연결하면 수강생은 기존 `npm run dev` 한 번으로 사이트와 지도를 함께 쓸 수 있고 정적 배포는 그대로 유지된다.

**Alternatives considered**:

- Astro 서버 렌더링과 어댑터 추가: 배포 방식과 의존성이 바뀌어 제외했다.
- 별도 지도 서버 실행: 수강생이 두 프로세스와 두 주소를 관리해야 하므로 제외했다.
- 브라우저 파일 접근 권한 요청: 브라우저별 지원과 반복 권한 승인에 의존하므로 제외했다.

**Primary references**:

- [Astro 4 Endpoints](https://v4.docs.astro.build/en/guides/endpoints/)
- [Astro Routing Reference](https://docs.astro.build/en/reference/routing-reference/)
- [Vite Plugin API — configureServer](https://vite.dev/guide/api-plugin.html#configureserver)

## 3. 변경 감지 방식

**Decision**: 운영체제 파일 감시 기능 대신, 요청할 때마다 작은 허용 목록을 다시 확인한다.

**Rationale**: 확인 대상은 전체 저장소가 아니라 100개 미만의 알려진 파일과 작은 폴더다. 2초 간격의 제한된 재확인은 5초 반영 조건을 넉넉히 만족하며 Windows·macOS·Linux의 파일 감시 차이와 watcher 정리 문제를 피한다. Node의 안정된 파일 시스템 API만 사용한다.

**Alternatives considered**:

- 파일 watcher: 운영체제별 이벤트 누락·중복과 재시작 처리가 수업용 MVP에 불필요한 복잡성을 더해 제외했다.
- 전체 저장소 재귀 탐색: 개인정보 경계와 성능 범위를 넓혀 제외했다.

**Primary reference**:

- [Node.js File system documentation](https://nodejs.org/api/fs.html)

## 4. 지도 렌더링

**Decision**: 현재 승인된 Archify 지도의 개념·세로 흐름·그룹 구성을 시각 참고로 삼되, 실행 시 Archify를 호출하지 않는다. 지도는 큰 글자의 의미 있는 HTML 카드와 가벼운 연결선으로 그린다.

**Rationale**: 정적 Archify 결과는 구조를 설명하는 데 효과적이었지만, 실시간 상태를 반영하려면 매 변경마다 외부 렌더링을 다시 돌리거나 큰 HTML을 교체해야 한다. 직접 렌더링하면 글자 크기, 대비, 세로 흐름, 상태 배지와 변경 강조를 학습 화면에 맞게 제어할 수 있다.

**Alternatives considered**:

- Archify를 수강생 PC에 설치하고 매번 재생성: 별도 설치와 재렌더 시간이 생겨 제외했다.
- D2 또는 Mermaid 런타임: 새 도구와 레이아웃 변동을 추가하고, 이미 겪은 작은 글자·과도한 가로 폭 문제를 다시 만들 수 있어 제외했다.
- 정적 이미지만 사용: 실제 실습 변경을 반영하지 못해 제외했다.

## 5. 상태와 검증 판정

**Decision**: `아직 만들지 않음`, `존재함`, `검증됨`, `확인 필요` 네 상태를 사용한다. `검증됨`은 구성요소별로 정의된 명시적이고 현재 유효한 근거가 있을 때만 허용한다.

**Rationale**: 파일이 있다는 사실은 작업 완료를 증명하지 않는다. 반대로 원본 템플릿에 개인화 파일이 없는 것은 오류가 아니라 수업 전 상태다. 존재·완료·오류를 분리해야 지도가 수강생에게 거짓 확신을 주지 않는다.

**Alternatives considered**:

- 있음/없음 두 상태: 완료와 누락의 의미를 설명하지 못해 제외했다.
- 파일명이나 최근 수정 시각만으로 검증 완료 추론: 허위 통과 가능성이 있어 제외했다.
- 임의 로그 파일을 모두 검증 근거로 인정: 어떤 결과를 증명하는지 연결할 수 없어 제외했다.

## 6. 응답 정보와 개인정보

**Decision**: 브라우저에는 프로젝트 기준 상대경로, 유형, 상태, 수정 시각, 연결 관계만 보낸다. 절대경로, 파일 본문, 환경 변수, Git 내부 정보는 보내지 않는다.

**Rationale**: 화면 녹화나 오프라인 수업에서 주소와 개인 경로가 노출될 수 있다. 지도 목적에는 파일 내용이 아니라 역할과 연결 상태만 필요하다.

**Alternatives considered**:

- 파일 본문 일부 표시: 설명은 쉬워지지만 민감정보와 화면 녹화 위험이 커 제외했다.
- 절대경로 표시: 문제 해결에는 편하지만 사용자명과 로컬 구조가 노출되어 제외했다.

## 7. 검증 전략

**Decision**: 실제 학습 파일을 만들고 지우는 대신 운영체제 임시 폴더의 작은 인공 템플릿으로 스캐너를 검사한다. 가벼운 자동 검사 후에만 빌드와 브라우저 육안 검사를 각각 한 번 수행한다.

**Rationale**: 사용자 파일을 건드리지 않고 생성·이동·삭제·중복·읽기 실패·범위 밖 파일을 반복 검증할 수 있다. 무거운 작업을 마지막 한 번으로 제한해 컴퓨터 반응성 규칙도 지킨다.

**Alternatives considered**:

- 개인화 복사본을 테스트 중 직접 변경: 수업 결과를 훼손할 수 있어 제외했다.
- 브라우저 자동화만 사용: 파일 판정 오류의 원인을 좁히기 어렵고 자원 사용이 커 제외했다.
