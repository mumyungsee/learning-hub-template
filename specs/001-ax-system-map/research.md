# Research: 실습용 AX 구조 지도

## 1. 구현 정본과 수업 복사본

**Decision**: 기능의 정본은 `course-renewal/template` Git 프로젝트에 둔다. 지난 수업에서 개인화된 `my-learning-hub` 복사본은 실제 파일 상태를 확인하는 검증 대상으로만 사용한다.

**Rationale**: 원본에 기능을 넣어야 다음 AX 강의에서도 다시 쓸 수 있다. 개인화 복사본을 정본으로 삼으면 대표님의 실습 결과와 공통 템플릿이 섞이고, 이후 수강생에게 배포할 때 매번 수작업으로 걷어내야 한다.

**Alternatives considered**:

- 개인화 복사본에만 구현: 이번 수업은 빠르지만 재사용과 배포가 깨져 제외했다.
- 아루나 사이트에 구현: 공개 사이트가 수강생 PC의 로컬 파일을 읽을 수 없고 콘텐츠·뷰어 분리 원칙에도 맞지 않아 제외했다.

## 2. 실시간 상태 전달 방식

**Decision**: 기존 Astro 개발 서버에 개발 전용 상태 경로를 얇게 연결하고, 지도 화면이 2초 간격으로 상태를 다시 요청한다.

**Rationale**: 현재 프로젝트는 Astro의 기본 정적 출력이다. Astro 공식 문서에 따르면 정적 엔드포인트는 빌드 시점에 생성되고, 요청 때 실행되는 서버 엔드포인트에는 서버 어댑터가 필요하다. 배포 구성을 서버 방식으로 바꾸면 이번 로컬 수업 도구보다 변경 범위가 커진다. 개발 서버에만 연결하면 수강생은 기존 `npm run dev` 한 번으로 사이트와 지도를 함께 쓸 수 있고 정적 배포는 그대로 유지된다.

**Alternatives considered**:

- Astro 서버 렌더링과 어댑터 추가: 배포 방식과 의존성이 바뀌어 제외했다.
- 별도 지도 서버 실행: 수강생이 두 프로세스와 두 주소를 관리해야 하므로 제외했다.
- 브라우저 파일 접근 권한 요청: 브라우저별 지원과 반복 권한 승인에 의존하므로 제외했다.

**Primary references**:

- [Astro 4 Endpoints](https://v4.docs.astro.build/en/guides/endpoints/)
- [Astro Routing Reference](https://docs.astro.build/en/reference/routing-reference/)
- [Vite Plugin API — configureServer](https://vite.dev/guide/api-plugin.html#configureserver)

## 3. 변경 감지 방식

**Decision**: 운영체제 파일 감시 기능 대신, 요청할 때마다 작은 허용 목록을 다시 확인한다.

**Rationale**: 확인 대상은 전체 저장소가 아니라 100개 미만의 알려진 파일과 작은 폴더다. 2초 간격의 제한된 재확인은 5초 반영 조건을 넉넉히 만족하며 Windows·macOS·Linux의 파일 감시 차이와 watcher 정리 문제를 피한다. Node의 안정된 파일 시스템 API만 사용한다.

**Alternatives considered**:

- 파일 watcher: 운영체제별 이벤트 누락·중복과 재시작 처리가 수업용 MVP에 불필요한 복잡성을 더해 제외했다.
- 전체 저장소 재귀 탐색: 개인정보 경계와 성능 범위를 넓혀 제외했다.

**Primary reference**:

- [Node.js File system documentation](https://nodejs.org/api/fs.html)

## 4. 지도 렌더링

**Decision**: Archify식 상세 구조 표현을 시각 참고로 삼되 실행 시 Archify를 호출하지 않는다. 지도는 승인한 여덟 고정 노드와 가벼운 연결선으로 그리고, 실제 상대경로는 마우스 올림과 선택 상세에 표시한다.

**Rationale**: 정적 Archify 결과는 구조를 설명하는 데 효과적이었지만, 실시간 상태를 반영하려면 매 변경마다 외부 렌더링을 다시 돌리거나 큰 HTML을 교체해야 한다. 직접 렌더링하면 구조의 위치는 고정한 채 상태 배지와 업무 전용 확장 노드만 갱신할 수 있다. 수강생은 같은 지도를 계속 보면서 무엇이 어느 자리에 추가됐는지 이해할 수 있다.

**Alternatives considered**:

- Archify를 수강생 PC에 설치하고 매번 재생성: 별도 설치와 재렌더 시간이 생겨 제외했다.
- D2 또는 Mermaid 런타임: 새 도구와 레이아웃 변동을 추가하고, 이미 겪은 작은 글자·과도한 가로 폭 문제를 다시 만들 수 있어 제외했다.
- 정적 이미지만 사용: 실제 실습 변경을 반영하지 못해 제외했다.
- 여러 보기 탭으로 구조를 나누기: 전체 관계와 누적 변화를 가려 수업 목적에 맞지 않아 제외했다.

## 5. 다른 PC에서의 실행

**Decision**: 지도 기능 전체를 수강생 템플릿에 포함하고, 각 PC가 자기 템플릿 폴더에서 기존 개발 서버를 실행해 자기 파일만 읽게 한다. 공통 `npm run map` 명령과 Windows용 한 번 실행 파일을 제공한다.

**Rationale**: 공개 웹사이트는 브라우저 보안상 수강생 PC의 로컬 파일을 읽을 수 없다. 반면 템플릿 안의 로컬 서버는 현재 실행한 프로젝트를 기준으로 이미 제한된 파일만 확인할 수 있다. 강사 PC와 수강생 PC는 서로 연결되지 않으며 같은 프로그램이 각자의 복사본을 독립적으로 읽는다.

**Alternatives considered**:

- 한 공개 주소에서 모든 수강생 PC 파일 확인: 브라우저 보안과 개인정보 경계를 위반해 제외했다.
- 별도 데스크톱 앱 설치: 이번 수업 범위를 크게 늘려 제외했다.

## 6. 상태와 검증 판정

**Decision**: `아직 만들지 않음`, `존재함`, `검증됨`, `확인 필요` 네 상태를 사용한다. `검증됨`은 구성요소별로 정의된 명시적이고 현재 유효한 근거가 있을 때만 허용한다.

**Rationale**: 파일이 있다는 사실은 작업 완료를 증명하지 않는다. 반대로 원본 템플릿에 개인화 파일이 없는 것은 오류가 아니라 수업 전 상태다. 존재·완료·오류를 분리해야 지도가 수강생에게 거짓 확신을 주지 않는다.

**Alternatives considered**:

- 있음/없음 두 상태: 완료와 누락의 의미를 설명하지 못해 제외했다.
- 파일명이나 최근 수정 시각만으로 검증 완료 추론: 허위 통과 가능성이 있어 제외했다.
- 임의 로그 파일을 모두 검증 근거로 인정: 어떤 결과를 증명하는지 연결할 수 없어 제외했다.

## 7. 응답 정보와 개인정보

**Decision**: 브라우저에는 프로젝트 기준 상대경로, 유형, 상태, 수정 시각, 연결 관계만 보낸다. 절대경로, 파일 본문, 환경 변수, Git 내부 정보는 보내지 않는다.

**Rationale**: 화면 녹화나 오프라인 수업에서 주소와 개인 경로가 노출될 수 있다. 지도 목적에는 파일 내용이 아니라 역할과 연결 상태만 필요하다.

**Alternatives considered**:

- 파일 본문 일부 표시: 설명은 쉬워지지만 민감정보와 화면 녹화 위험이 커 제외했다.
- 절대경로 표시: 문제 해결에는 편하지만 사용자명과 로컬 구조가 노출되어 제외했다.

## 8. 검증 전략

**Decision**: 실제 학습 파일을 만들고 지우는 대신 운영체제 임시 폴더의 작은 인공 템플릿으로 스캐너를 검사한다. 가벼운 자동 검사 후에만 빌드와 브라우저 육안 검사를 각각 한 번 수행한다.

**Rationale**: 사용자 파일을 건드리지 않고 생성·이동·삭제·중복·읽기 실패·범위 밖 파일을 반복 검증할 수 있다. 무거운 작업을 마지막 한 번으로 제한해 컴퓨터 반응성 규칙도 지킨다.

**Alternatives considered**:

- 개인화 복사본을 테스트 중 직접 변경: 수업 결과를 훼손할 수 있어 제외했다.
- 브라우저 자동화만 사용: 파일 판정 오류의 원인을 좁히기 어렵고 자원 사용이 커 제외했다.

## 9. 템플릿 바탕과 이번 업무 구분

**Decision**: 매니페스트의 제한된 탐색 결과는 `기본 제공`으로만 취급한다. 이번 업무는 선택적으로 존재하는 `.workspace-map/active-work.json`이 업무 이름과 구성요소별 정확한 상대경로를 가리킬 때만 인정한다.

**Rationale**: 템플릿에는 수업을 시작하기 위한 지침·스킬·예시·검사 파일이 이미 많이 들어 있다. 이 파일들의 존재를 곧바로 수강생의 업무 구현 상태로 보면 아무 작업도 하지 않았는데 모든 것이 준비된 것처럼 보인다. 작은 포인터를 정본으로 두면 명세·스크립트·결과물이 서로 다른 폴더에 있어도 원본을 복사하지 않고 한 업무로 묶을 수 있으며, 생성 시각이나 파일명에 기대는 불안정한 추론도 피할 수 있다.

**Alternatives considered**:

- 최근 수정된 파일을 이번 업무로 간주: 템플릿 업데이트와 실제 수강생 작업을 구분할 수 없어 제외했다.
- 업무 전용 폴더로 모든 원본 복사: 한 사실이 여러 곳에 생기고 경로가 깨질 위험이 있어 제외했다.
- 모든 파일에 업무 메타데이터 추가: 기존 지침·스크립트 형식을 광범위하게 바꿔야 하므로 제외했다.

## 10. 고정 기반 노드와 업무 전용 확장 노드

**Decision**: 템플릿의 기본 구조를 하나의 고정된 통합 지도로 유지한다. 명세·검증·결과·인계처럼 이미 기본 흐름에 자리가 있는 산출물은 고정 노드의 상태와 상세만 갱신하고 별도 노드로 복제하지 않는다. 현재 업무 때문에 새로 만든 업무 전용 스킬·스크립트·MCP 같은 실행 확장만 대응하는 고정 노드 주변에 가지 노드로 붙인다. 하나의 확장 노드는 여러 원본 파일을 가리킬 수 있다.

**Rationale**: 같은 큰 상자 안에 긴 파일 목록을 함께 넣으면 읽기 어렵지만, 기본 흐름의 명세·결과·인계까지 모두 새 노드로 만들면 기존 흐름과 새 업무 흐름이 나란히 생겨 투트랙처럼 보인다. 기본 흐름은 한 번만 두고 새 실행 능력만 가지로 보여야 수강생이 ‘원래 있던 운영 방식’과 ‘이번 업무를 위해 추가한 자동화’를 바로 구분할 수 있다.

**Alternatives considered**:

- 고정 노드 안에 두 개의 파일 목록 유지: 구분이 작고 내부 스크롤이 필요해 제외했다.
- 파일 하나마다 동적 노드 생성: 같은 스킬의 코드·설정·설명 파일이 흩어져 보이고 노드 수가 지나치게 늘어 제외했다.
- 별도 탭이나 위아래 두 구획으로 템플릿과 현재 업무 분리: 두 구조가 서로 다른 시스템처럼 보이고 실제로 어느 자리에 무엇이 붙었는지 바로 알기 어려워 제외했다.
- 기본 명세·검증·결과·인계까지 모두 사용자 노드로 분리: 기존 흐름을 한 번 더 그려 투트랙처럼 보여 제외했다.

## 12. 실제 학습메이트 지침 연결

**Decision**: 고정 지도는 `도구별 입구 → 공통 지침·맥락 → 명세`의 역할을 유지한다. `CLAUDE.md`·`GEMINI.md` → `AGENTS.md` → `SOUL.md`·`USER.md`·스킬 규칙의 실제 연결은 고정 노드의 상세에서 설명하고 별도 신규 노드로 복제하지 않는다. Codex가 `AGENTS.md`를 직접 읽는다는 차이도 같은 상세에 둔다.

**Rationale**: 개인화된 학습 허브에는 이 파일들이 이미 있으며 `CLAUDE.md`와 `GEMINI.md`는 각각 `@AGENTS.md` 한 줄, `AGENTS.md`는 `SOUL.md`와 `USER.md`를 읽고 요청에 맞는 스킬을 사용하라는 규칙을 가진다. 이번 업무에서 새로 만드는 것이 아니므로 별도 초록 노드로 표시하면 ‘새 자동화’와 혼동된다.

**Alternatives considered**:

- 다섯 파일을 모두 새 업무 노드로 표시: 이번 업무에서 만든 자동화처럼 보여 제외했다.
- 지도 본문에 다섯 파일명을 긴 목록으로 표시: 구조를 복잡하게 하므로 고정 노드 선택 상세에만 둔다.

## 13. PKM 장기 지식 재사용 순환

**Decision**: PKM은 결과 뒤에 멈추는 종착점이 아니라 `결과물 → 정제·저장 → PKM → 다음 업무의 공통 지침·맥락`으로 되돌아오는 선택적 순환으로 표시한다.

**Rationale**: `HANDOFF.md`는 현재 업무를 다른 세션이 이어받기 위한 상태이고, PKM은 여러 업무에서 다시 쓸 수 있도록 정제한 장기 지식이다. 두 요소를 모두 마지막 산출물처럼 놓으면 현재 업무의 재진입과 장기 지식 재사용을 구분할 수 없다.

**Alternatives considered**:

- PKM을 결과물 옆의 끝 노드로만 표시: 다음 업무에서 다시 쓰는 핵심 의미가 사라져 제외했다.
- PKM에서 명세로 바로 연결: 실제로는 관련 지식을 먼저 현재 맥락으로 불러온 뒤 새 명세에 반영하므로 공통 지침·맥락으로 되돌린다.

## 11. 시각 시안 우선 승인

**Decision**: 실시간 스캐너와 현재 업무 포인터를 바꾸기 전에, 가짜 예시 데이터만 사용하는 별도 정적 화면에서 새 노드 구조를 먼저 검토한다.

**Rationale**: 구조도의 교육적 의미와 레이아웃이 승인되지 않은 상태에서 상태 계약까지 바꾸면, 시각 수정이 데이터 모델과 테스트를 반복해서 흔든다. 별도 시안은 기존 실시간 지도를 보존하면서 경계, 노드 크기, 연결 방식, 경로 상세 표현만 빠르게 판정할 수 있다.

**Alternatives considered**:

- 기존 실시간 화면을 바로 수정: 되돌릴 범위와 검증 비용이 커 제외했다.
- 문서 그림만 검토: 마우스 올리기와 선택 상세 같은 실제 상호작용을 판단할 수 없어 제외했다.

## 14. 승인 뒤 실시간 계약 이전

**Decision**: 승인한 시안을 실시간 상태 계약 3번과 현재 업무 포인터 2번으로 옮긴다. 포인터의 `artifacts`는 명세·검증·결과·인계 고정 노드만 갱신하고, `extensions`는 스킬·스크립트·MCP·API·DB·PKM 중 지원 경로를 명시할 때만 별도 노드를 만든다.

**Rationale**: 고정 산출물과 새 실행 능력을 데이터 단계에서 분리해야 화면이 다시 투트랙으로 퇴행하지 않는다. 확장 종류가 붙을 고정 자리를 정하므로 포인터가 임의 관계를 만들어 구조를 왜곡할 수도 없다.

**Alternatives considered**:

- 기존 포인터 1번에 `harness` 파일을 계속 섞기: 어떤 파일이 별도 노드가 되어야 하는지 구분할 수 없어 제외했다.
- 프로젝트 밖 PKM 절대경로를 직접 읽기: 개인정보 노출과 범위 이탈 위험이 있어 제외했다. 실제 외부 PKM은 프로젝트 안의 제한된 어댑터 파일로 연결한다.
